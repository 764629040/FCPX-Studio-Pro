## 2. A-1 旋转文本方向丢失

### 2.1 根因

任务单指出 `core/psd_parser.py:763/888` 把 `rotation` 硬编码为 `0.0`。实际核验后根因有两层：

1. **解析层**：从未读取 `layer.transform`，`rotation` 恒为 `0.0`。
2. **绘制层**（任务单未点名，但同样必需）：`gui/canvas_view.py` 的 `update_geometry_from_info()` 没有应用任何旋转，且用「文本字符数 × 字号」反推宽高。竖排文本因此被画成横排且尺寸失真，越出画板。

仅修解析层而不修绘制层，画面依然是横排，因此两层同修。

### 2.2 PSD 真实数据（psd_tools 实测）

`complex_layers.psd` 两个目标图层的仿射矩阵：

| 图层 | transform (a,b,c,d,tx,ty) | atan2(b,a) | bbox | 形态 |
|---|---|---|---|---|
| `Text01` | `(2.1e-16, 1.0, -1.0, 3.6e-16, …)` | **90.0°** | `(75,164,106,929)` | 31×765 细高 |
| `Title` | `(2.1e-16, 1.0, -1.0, 3.6e-16, …)` | **90.0°** | `(1651,101,1839,899)` | 188×798 细高 |

### 2.3 修复实现

**`detect_layer_rotation(layer)`**（`core/psd_parser.py`）：

```python
a, b = float(transform[0]), float(transform[1])
if abs(a) < 1e-9 and abs(b) < 1e-9:
    return 0.0                      # 线性部分退化
angle = math.degrees(math.atan2(b, a)) % 360.0
for cardinal in (0.0, 90.0, 180.0, 270.0, 360.0):
    if abs(angle - cardinal) <= 2.0:   # ±2° 容差吸附
        return cardinal % 360.0
return round(angle, 4)              # 非正交角保留精确值
```

接入两个构造点：

- 文本图层：`layer_rotation = detect_layer_rotation(layer)` → `rotation=layer_rotation`
- 降级图层：`rotation=detect_layer_rotation(layer)`

**绘制层**（`gui/canvas_view.py`）：

```python
rotation = float(getattr(info, "rotation", 0.0) or 0.0)
if rotation:
    # 按原稿 bbox 校正旋转后矩形（不再用文本长度反推）
    if rotation % 180 == 90:
        self.setRect(-bh/2.0, -bw/2.0, bh, bw)
    else:
        self.setRect(-bw/2.0, -bh/2.0, bw, bh)
    self.setTransformOriginPoint(0.0, 0.0)
    self.setRotation(rotation)
else:
    self.setRotation(0.0)
```

### 2.4 验证结果

| 图层 | rotation | 渲染外接框 | 画板内 | 形态 |
|---|---|---|---|---|
| `Text01` | 90.0° | 32 × 766 | ✅ | 竖排细高 |
| `Title` | 90.0° | 189 × 799 | ✅ | 竖排细高 |

修复前两者渲染为横排且 `Title` 越出右边界；修复后恢复竖排且完整位于画板内（画板 1920×1080，`Title` 外接框 x∈[690,880]，画板右界 960）。

### 2.6 一处必须说明的认知修正

我最初写了「未旋转图层 rotation 必须为 0」的断言，结果在 `vertical_wedding_9_16.psd` 上失败。核查后发现**是我假设错了**：该竖版海报中西文图层（`lead the presentation`、`THE BRIDE`、`THE GROOM`、`CITY`）本身就是 `[[0,1],[-1,0]]` 的 90° 竖排，只有中文层是 0°。属于夹具真实特征，不是代码缺陷。

已将该断言改为「旋转角必须与 transform 推导值和 bbox 形态三者自洽」，这才是正确的判定依据。

## 3. A-2 处置原因未按四态分化

### 3.1 根因

`core/psd_parser.py` 中 preserved 文本图层的 `reason` 是单一硬编码字符串：

```python
reason = "纯矢量文本，字体元数据完整，保留为可发布标题"
```

四种字体状态共用此句，导致诊断表出现「`font_missing（缺 1 字）`」与「字体元数据完整」同一行自相矛盾。

### 3.2 修复实现

抽出 `build_preserved_reason(font_status, missing_glyphs, fallback_font)`，由解析器调用，测试也直接调用同一实现（不复制文案逻辑）：

| 状态 | 文案 |
|---|---|
| `complete` | 纯矢量文本，字体与字形均完整，保留为可发布标题 |
| `partial_missing` | 纯矢量文本，字体已安装但缺 {N} 个字形，已标记待替换 |
| `font_missing` | 纯矢量文本，原始字体未安装、缺 {N} 字，已降级为回退字体 '{X}' 并标记待处理 |
| `unverifiable` | 纯矢量文本，当前平台无法枚举字体字形，缺字风险无法确定，已保留矢量并标记待复核 |

缺字数量由 `len(missing_glyphs)` 实时统计，未写死。

### 3.3 验证结果

| 检查项 | 结果 |
|---|---|
| 四态文案两两不同 | ✅ `True` |
| 含"元数据完整"的行数 | ✅ **0** |
| `font_missing` 含"未安装"+"缺 N 字"+"回退字体" | ✅ |
| 真实 PSD 中 reason 与 font_status 自洽 | ✅ |

注：当前机器字体未注册，真实 PSD 只出现 `font_missing` 一态；四态同屏由 `build_preserved_reason` 直接驱动验证（测试调用真实实现，非复制文案）。

截图：`docs/16_A2四态原因分化修复验证.png`
