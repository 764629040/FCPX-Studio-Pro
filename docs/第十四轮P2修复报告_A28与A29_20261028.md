## 1. A-28：缩略图硬编码导致竖版拉伸（已修复）

### 1.1 根因核实

`core/thumbnail.py` 两处函数均硬编码：

```python
large_img = img.resize((640, 360), Image.Resampling.LANCZOS)
small_img = img.resize((192, 108), Image.Resampling.LANCZOS)
```

对 1080×1920 竖版：横向被拉伸到 640（原应按比例 360），**拉伸倍数 3.16**。审核判断准确。

### 1.2 修复

新增等比缩放函数，按**长边**缩放、保持源画幅：

```python
def fit_thumbnail_size(src_w, src_h, long_edge) -> tuple:
    """按长边等比缩放，保证短边不被拉伸"""
    if src_w >= src_h:
        w = long_edge
        h = max(1, int(round(long_edge * src_h / src_w)))
    else:
        h = long_edge
        w = max(1, int(round(long_edge * src_w / src_h)))
    return w, h
```

两处生成函数（PSD 合成 / PIL Image）均改用该函数。

### 1.3 验证

| 源画幅 | 源比例 | large 输出 | 比例偏差 |
|---|---|---|---|
| 1920×1080（横） | 1.778 | **640×360** | **0.00%** |
| 1080×1920（竖） | 0.562 | **360×640** | **0.00%** |
| 1080×1080（方） | 1.000 | **640×640** | **0.00%** |
| 3840×2160（4K） | 1.778 | 640×360 | 0.00% |

**兼容性**：16:9 源仍产出 640×360 / 192×108，与旧行为完全一致。

证据：`docs/round14_evidence/a28_a29_verify.json`

## 2. A-29：所谓"竖版"夹具实为横版（已修复）

### 2.1 根因核实（比审核描述更具体）

| 检查项 | `vertical_wedding_9_16.psd` 实测 |
|---|---|
| 画布 | 1080×1920（竖） |
| **背景层 bbox** | **(0, 0, 1920, 1080)** ← 横版尺寸 |
| 越界量 | 右 840、下 -840 |
| 8 层文字纵向中心均值 | **464**（画布中心是 **960**） |
| 合成图异常像素 | **纯红 84 个 + 纯绿 40 个** |

**三条独立证据一致证明**：这是横版内容被塞进竖版画布，只是改了画布头。

**后果确认**：`psd-tools` 在 bbox 越界时读错像素，合成图出现红绿彩条，
`large.png` 因此是乱码。

### 2.2 修复：生成几何自洽的真竖版夹具

新增 `tests/make_vertical_true_fixture.py`，产出 `tests/data/vertical_9x16_true.psd`：

| 项 | 值 |
|---|---|
| 画布 | 1080×1920 |
| 背景层 bbox | **(0, 0, 1080, 1920)** ← 严格不越界 |
| 文本层数 | 8 |
| 文字纵向中心 | 261 → 1658，均匀分布，跨越画布中线 |
| 合成图异常像素 | **纯红 0 / 纯绿 0** |

**不改动原夹具**——保留 `vertical_wedding_9_16.psd` 以免影响已过审的 137 项测试，
新夹具独立命名并纳入指纹清单。

### 2.3 技术细节：PSD 层名不支持中文

`psd-tools` 写层名走 **macroman** 编码，中文会抛 `UnicodeEncodeError`。
因此新夹具层名用 ASCII（`Text 01`…`Text 08`），**中文原名与文本内容
记录在旁路文件** `tests/data/vertical_9x16_true.json`，供测试对照。
