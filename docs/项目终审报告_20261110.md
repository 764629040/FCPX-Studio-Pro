## 四、风险提示与后续建议

1. **磁盘是最大隐患**。卷剩 259 MB，`.git` 占 181 MB、`python_bundle` 占 140 MB。建议顺序：先定 scipy 63 MB 去留 → 再谈 `.git` 历史压缩（需你授权重写）→ 最后才动报告历史截图。250 个 `index.lock.bak_*` 全是 0 字节，删了只清爽，省不出空间。
2. **每轮测试必须自清**。本轮抓到三处执行方留下的测试垃圾：`Titles.localized/TR009验证`（264K，直接留在了你的真实模板库）、禁用仓 0B 空骨架、备份仓 5 份测试备份。已由我清除，但"测完自清"要写进执行侧纪律，否则你今天删一批、明天又长一批。
3. **备份与禁用仓的位置不能再回退**。备份必须固定在 `~/Library/Application Support/FCPXStudio/backups/`，禁用仓固定在 `.../disabled/`，两者都不得落在 `~/Movies/Motion Templates.localized` 内。这是 TR-009 的根因，也是最容易被后续改动破坏的约定。
4. **迁移逻辑的边界要长期守住**。只迁移含 `.moti/.moef/.motr/.motn` 的目录，绝不动 bundle 内部 `.disabled`（框架的 `Resources.disabled` 是版本化符号链接，搬走会坏插件）。本轮执行侧确实踩过这个坑，已还原并加固，但下次改迁移代码必须重跑这条断言。
5. **`.disabled` 相关残留代码可以留但要标死**。`TemplateTier.swift:430/498` 仍在判定 `.disabled` 后缀，新机制下已无意义；建议加注释标明"仅历史兼容，FCPX 不认，勿再启用该方案"。
6. **永久禁止"自动重启 FCPX"类功能**（用户 2026-11-10 明确否决）。理由：剪辑中时间线未存盘，任何自动退出 FCPX 的动作用都可能让工程进度丢失；禁用只做文件系统操作，FCPX 是否重启由用户自己决定。后续任何人提"顺手帮你重启 FCPX 让改动生效"，一律驳回。
7. **误触禁用是有代价的**。禁用会把模板移出 FCPX 可见范围，若某个正在编辑的工程引用了它，重启 FCPX 后该片段可能显示缺失（模板文件本身没删、可随时启用回来）。因此禁用需要二次确认，这一步不是体验优化，是数据安全。
