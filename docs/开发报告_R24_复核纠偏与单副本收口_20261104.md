## 2. A-44 反证：从 4 个 .ips 提取 backtrace，查模板装载路径

**R23 旧结论的问题：** 仅以"grep 不到模板路径字符串"就断言"无关"——属过度推断。

**R24 修正方法：** 正确解析 `.ips`（双 JSON 段 + 清洗 NaN/Infinity，见 A-45），抽取 `faulting` 线程栈，判断是否落在 FCP 装载 Motion 模板文档的路径（OZScene / OZDocument / FFMotionEffect / TXText / OZChannel）。

**复跑命令与输出（节选，完整见 `docs/r24_evidence/crash_logs_r24.txt`）：**

```bash
python3 docs/r23_evidence/scan_crashlogs.py
```

| 日志 | 时间 | EXC | SIGNAL | faulting 线程 | 是否模板装载路径 | 项目路径标记 |
|---|---|---|---|---|---|---|
| `2026-11-02-230733.ips` | 11-02 23:07 | EXC_BAD_ACCESS | SIGSEGV | 32 | **True** | NONE |
| `2026-11-03-174024.ips` | 11-03 17:40 | EXC_CRASH | SIGABRT | 5 | False | NONE |
| `2026-11-03-174131.ips` | 11-03 17:41 | EXC_CRASH | SIGABRT | 24 | False | NONE |
| `2026-11-03-174443.ips` | 11-03 17:44 | EXC_CRASH | SIGABRT | 3 | False | NONE |

**11-02 崩溃的 faulting 线程栈顶（节选）：**

```
#0  OZChannel::getValueAsDouble(CMTime const&, double) const   <== template-load
#1  OZChannel::getValueAsInt(CMTime const&, double) const       <== template-load
#2  TXTextLayout::applyAllCaps(__CFString*)
#3  TXTextLayout::updateDisplayString(CMTime const&)
#4  TXTextLayout::didFinishLoadingIntoScene()
#7  OZScene::parseEnd(PCSerializerReadStream&)
#11 OZDocument::open(PCURL const&)
#13 -[FFMotionEffect _backgroundLoadDocument:onTask:]           <== template-load
```

**诚实结论（非"全无关"、亦非"全是模板"）：**
- **11-02 `SIGSEGV`**：崩溃确实发生在 **FCP 后台装载 Motion 模板文档**的过程中（`FFMotionEffect _backgroundLoadDocument → OZDocument::open → OZScene 解析 → 文本布局 → OZChannel::getValueAsDouble` 空指针），与"坏模板装载/解析失败"失效模式吻合——**复核方对该条的质疑成立，不能称"无关"**。
- **但日志不含任何具体模板路径字符串，无法归因到 T01/T23 或 2..50 中某一个**；它也可能是 FCP 后台装载的任意一个标题模板。
- **11-03 ×3 `SIGABRT`**：栈在 Core Data 目录库（`FFCatalogStore` / `FFMediaEventProject` / `DSBridge`），是数据层未捕获异常 `abort()`，**确与模板装载路径无关**。

## 3. A-45 修复：崩溃扫描脚本四项字段

**根因：** `.ips` 实为「第 1 行 header JSON」+「第 2 行起 body JSON」两段；旧脚本对整个文本 `json.loads` 直接失败（且 body 寄存器值含 `NaN/Infinity`，标准 `json` 拒绝），导致 `PROC/TIME/EXC/SIGNAL` 全输出 `?`。异常信息在 `exception.{type,signal}`（无 `exceptionType` 键），旧脚本取错键。

**修复：** 重写 `docs/r23_evidence/scan_crashlogs.py` —— 分段解析 + NaN 清洗 + 取 `exception.type`(EXC) / `exception.signal`(SIGNAL) / `header.timestamp`(TIME) / `header.app_name`(PROC)，并提取 faulting 线程帧与模板装载模块命中。

**修复后输出（四项字段已填充，见上表与 `docs/r24_evidence/crash_logs_r24.txt`）：**
- PROC 全部 = `Final Cut Pro`
- TIME 全部解析成功（11-02 23:07 / 11-03 17:40 / 17:41 / 17:44）
- EXC/SIGNAL 全部解析成功（EXC_BAD_ACCESS/SIGSEGV、EXC_CRASH/SIGABRT）
- `in_template_load` 字段区分了 11-02（True）与 11-03×3（False）

## 4. A-42 残留回应（正面回答，不回避）

### 4.1 为什么 `1` 和 `23` 在 ~/Movies 缺席？

**命令与输出：**

```bash
B="$HOME/Movies/Motion Templates.localized/Titles.localized/PSD婚礼字幕"
for x in 1 23; do [ -d "$B/$x" ] && echo "$x EXISTS" || echo "$x ABSENT"; done
# 1 ABSENT
# 23 ABSENT
ls -d "$B"/[0-9]* | wc -l
# 48   <== 即 2..50
```

- 用户独立库是 `2`..`50`（共 48 个），由 `PSD转Motion工具`/`批量体检` 于 2026-10-19 生成。**`1` 和 `23` 在该独立库中从未被创建**（用户自己的编号从 2 起、且跳过了 23），并非被谁删除。
- MVP 模板命名为 `T01_领衔呈现_竖版` 与 `T23_含装饰_横版`（**T 前缀**），与裸数字 `1`/`23` 在目录名层面本就不冲突。
- 因此 R22 担心的"T01 会移走你的 `1` 号模板"这一前提取消：① `1` 不存在；② 即便存在，R23 内容级判据（`_confirm_homology`）也只在"sha 一致/结构同源/空壳"时才移动，对内容独立的模板默认不移动。

### 4.2 是否对 ~/Movies 做过任何移动？

**没有。** 去重逻辑（`dedup_before_install`）只在 `core/motion_builder.build_template_atomic` **安装新模板时**触发，我从未对 `~/Movies` 调用过该流程。

```bash
find "$HOME/Movies" -type d \( -name "*_trash_*" -o -name ".*_trash_*" \) | wc -l
# 0   <== 全 ~/Movies 无任何隐藏回收/备份目录
```

若将来安装流程真在 `~/Movies` 产生回收目录，会在此处留下 `.{name}_trash_<ts>`；当前计数为 0，证明未发生任何移动。

### 4.3 "48 个编号模板"这层体验（正面回应）

用户看到的"很多个版本" = `T01` + `T23` + `2`..`50`（共 52 个 MVP/独立目录 + 2 个其他）同处 `Titles.localized/PSD婚礼字幕/` 下。**FCPX 会把该分类下所有子目录扁平展示在同一个"字幕"浏览器列表里**，于是用户产生"一堆重复版本"的观感。

事实：
- 这 48 个 `2`..`50` 是用户**自己 10-19 生成的独立纯文本标题库**（mtime 统一 10-19，`refMedia=no`，空 Media 正常），**与 MVP 的 T01/T23 在内容上无同源关系**。
- 它们**不是** T01/T23 的多版本残留（R23 清单已证实 `~/Movies` 无任何同名/同源多版本）。
- R23 内容级判据保证：安装 T01/T23 时，这 48 个目录因"名称别名但内容独立"而进入 `kept`（默认不移动），**会正常保留**，不会误删。
