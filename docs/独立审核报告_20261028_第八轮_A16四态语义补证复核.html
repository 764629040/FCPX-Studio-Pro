2.2 像素级互斥验证（关键证据）

对两张核心截图做最近邻颜色分类（阈值 70，排除顶栏区域）：

颜色 macOS 四态截图 无 AppKit 截图

红与黄严格互斥。 这一点意义重大：

同一个字体 CormorantInfant-Regular，

  • 在 macOS（有 AppKit，能真正查询字体表）→ 判为红：字体未安装；
  • 在无 AppKit（无检测能力）→ 判为黄：无法验证。

这正是 A-10 修复要达成的核心区分。 修复前布尔接口会把两者压成同一个「False / 字体缺失」， 现在两者在界面上是两种颜色、两种文案。A-16 的验证目标已达成。

说明（如实披露一处方法局限）：橙 #FF9F0A 与黄 #FFD60A 的 RGB 曼哈顿距离仅 55， 首轮用阈值 90 粗筛时二者会混淆，故改用最近邻分类 + 阈值 70，并以「红/黄互斥」为主结论， 不依赖橙黄可分。这是审核方主动收紧口径，不是开发方的问题。

3. unverifiable 用拦截构造取证：可接受，不必重做

3.1 开发方的顾虑是对的

macOS 自带 AppKit，程序在真机上永远不会自然进入 unverifiable 分支。 因此要在 macOS 上拍到该态，只能人为制造「检测能力不可用」。这是平台事实，不是取巧。

3.2 为什么仍然可接受——审核方已独立复现

审核方所处环境 import AppKit 真实失败（非拦截、非模拟），在此直接运行生产函数：

AppKit: NOT importable  → 真·无 AppKit 环境
parse_psd_file('tests/data/four_state.psd') → 8 个文字层
detection_status 集合 = {unverifiable}   （8/8 层）

在不使用任何拦截的前提下，第四态被真实触发。 这补上了开发方唯一缺失的那一环：

  • 拦截只负责「让程序走进这个分支」；
  • 走进去之后的判定逻辑与真机无 AppKit 完全相同；
  • 而「走进去之后是否正确」这件事，已由审核方的真实无 AppKit 环境独立证实。

3.3 裁定

该截图作为「第四态 UI 呈现」的证据成立，不需改用隔离进程方案。

开发方提出的备选方案（隔离进程注入 + 进程级证据）没有必要执行—— 那只是在同一个原理上再加一层日志，并不能提供比「真实无 AppKit 环境复现」更强的证据。 审核方已用更强的证据替代，此事可结。

但要求如实标注（报告中已满足，特此确认）：该截图性质为 「等价环境构造 + 第三方真环境交叉验证」，不得表述为「macOS 真机实拍」。 开发方原文已主动披露这一点，表述准确，值得肯定。

4.1 「该字体确实不存在」的证据强度：充分

开发方用三套互不依赖的系统机制交叉确认 CormorantInfant-Regular 不存在： AppKit 字体表查询 / NSFont 实例化失败 / atsutil 命令行枚举。

审核方复核：该结论与「红徽章出现在 macOS 截图中、且同字体在无 AppKit 下转为黄」的像素证据 一致——若字体其实存在，macOS 侧应显示绿而非红。两条独立证据链同向，结论成立。

4.2 字形缺失判定可信

glyph_proof 显示 Helvetica 渲染中文的覆盖率 0%，即「字体在、但字不在」。 这与「橙徽章出现在新娘 朱永宏图层」精确对应。该态判定正确。

7. A-15 决策建议（用户征询审核方意见）

结合本轮四态截图可直接观察到的实况：44% 缩放下，竖版多图层的徽章在垂直方向堆叠碰撞 （新郎的红色横徽与镇雄的多枚徽章挤成一团），确实已影响可读性，且并非靠调宽度可解。

审核方建议按以下优先级择一（均为设计层面的呈现方式变更，非架构改造）：

  1. 【推荐】改为「选中/悬停才展开徽章，常态仅显示 4px 色点」
    • 优点：彻底消除遮挡；诊断信息不丢失（点一下就看到）；同一套四色语义直接复用，改动面小；
    • 代价：需一次悬停/选中交互，但那是诊断场景的自然动作。
  2. 备选：徽章移入右侧图层树，逐行显示状态列；画布上仅留色点。
    • 优点：信息密度最高，可一次扫完所有图层状态；
    • 代价：改动面较大，需要图层树支持状态列。
  3. 不推荐：继续调字号/宽高/间距——历史上已证明必然失败（根因在高度方向 22px > 行距 11–14px）。

审核方结论：A-15 建议采用方案 1，作为 P2 设计变更立项；不阻塞真机验收。
