## 三、A-56 产品 bug 修复 —— 通过（本轮最高价值项）

### 3.1 根因与修复（我读源码核）

```python
# core/psd_parser.py:1006
font_substituted = (fallback_font != original_font)
```

注释明确：「旧实现比较的是 `fallback_target`（推荐目标），导致字体完全可用时也报『已替换』——真机 macOS 下每个中文层都会误报。无 AppKit 环境恰好掩盖了它。」

**这是一个真 bug，且性质严重**：`font_substituted=True` 会让用户以为每个中文层都被换过字体。而它被掩盖的原因是——没有 AppKit 的环境走不到这条分支，所以**此前 100% 的测试都碰不到**。

### 3.2 语义正确性验证

`docs/r28_evidence/a56_font_substituted_after.txt` 显示修复后四态：
- `detected` 层（字体完全可用）→ `substituted = False` ✅（修复前为 True）
- 缺字层 → `substituted = True` ✅（语义保留）

**修复精准，没有一刀切改成 False。**

## 七、新观察（2 项 P3 / 1 项已自报）

### A-59（P3）`has_missing_glyphs` 语义混用

`core/psd_parser.py:988` 直接令 `has_missing_glyphs = has_missing_risk`。在 `unverifiable` 状态下会出现：

```
has_missing_glyphs = True   但   missing_chars = []
```

→ 字段名说「有缺字」，实际含义是「有缺字风险（未验证）」。**我实测复现了这个组合。** 目前不影响 UI（tooltip 对空清单有兜底），但字段语义有歧义，未来若有人按 `has_missing_glyphs` 做统计会算错。建议拆成 `has_missing_glyphs`（确证）与 `has_missing_risk`（含未验证），或改名。

### A-60（P3，开发方已自报）指纹不覆盖 Swift / .app

我核实属实：r28 指纹 110 项中，**`FCPXStudioNative/**` 0 项、`.app`/二进制 0 项**。本轮 A-51 的主要成果（3 个 Swift 文件 + 重建二进制）**完全在指纹视野之外**。

**开发方的处理是正确且诚实的**：没有擅自扩大工具范围（那会让 110 项基线失效、造成跨轮不可比），而是**用二进制 sha256 直证来补**。但这是个结构性缺口——**交付物改了指纹却不知道，等于盲区**。建议后续把「二进制产物 sha + 构建时间戳」作为一组独立清单纳入（不与源码 110 项混算）。

### 关于「缺失字形」不在二进制（开发方主动披露的异常）

我独立复现了这个现象：

```
缺失字形:              utf8=0  utf16le=0
预览（□ 表示缺字）:      utf8=1  utf16le=0
```

且确认源码里**确实有** `缺失字形` 字面量（`InspectorView.swift:358` tooltip 拼装）。开发方用最小 Swift 程序复现，证明运行时 `print` 输出正确，仅该字面量不以连续字节存储。

**我的判断**：解释可信（Swift 对某些字面量确实走非连续存储），但**本沙箱无 swift 工具链，我无法重编译复核**。因此这项记为「开发方主动披露 + 已自证 + 我方无法独立验证」，**不列缺陷**——主动披露异常并给出复现实验，这个态度应鼓励。
