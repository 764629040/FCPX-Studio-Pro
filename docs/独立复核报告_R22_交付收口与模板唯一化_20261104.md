## 二、新缺陷 A-41（P1）：去重引擎会移走用户独立模板

### 2.1 缺陷机制

生产代码 `core/motion_builder.py` 第 701 行：

```python
_aliases = extra_aliases or derive_template_aliases(template_name)
```

**默认即自动派生别名。** 而 `derive_template_aliases("T01_领衔呈现_竖版")` 实测返回：

```
['01_领衔呈现', '1', '1_领衔呈现', 'T01_领衔呈现', '领衔呈现']
```

其中 **`'1'` 是裸编号**。`dedup_before_install` 对命中别名的兄弟目录**无条件移入回收站**（`reason` 仅作标签，不参与判定）。

### 2.2 审核方构造实验（决定性证据）

模拟用户 `~/Movies/PSD婚礼字幕` 的真实结构：`1`（用户独立模板，内容与 T01 不同）、`01_领衔呈现`（旧版）、`T01_领衔呈现_竖版`（目标）。执行去重后：

```
别名集合 = ['01_领衔呈现', '1', '1_领衔呈现', 'T01_领衔呈现', '领衔呈现']
安装前目录 = ['01_领衔呈现', '1', 'T01_领衔呈现_竖版']

--- 处置报告 ---
  移走: 1              reason=同名/同源历史版本，多版本并存风险  sha=N/A
  移走: 01_领衔呈现     reason=同名/同源历史版本，多版本并存风险  sha=N/A

安装后目录 = ['.T01_领衔呈现_竖版_trash_20261104_081654', 'T01_领衔呈现_竖版']

!!! 用户的独立模板 '1' 是否被移走: 是 → 误伤（危险）
```

**判定：用户 FCPX 中名为 `1` 的模板，会在下一次安装 T01 时被移入回收站。** 这是 R22 自身引入的回归，比原缺陷更危险——原缺陷是多版本共存（用户可见、可辨），新缺陷是**静默移走用户认为正常的模板**。

### 2.3 更严重：该行为已被测试固化为「正确」

`tests/test_r22_a40_dedup.py` 第 78 行：

```python
assert "1" in moved_names, f"历史版本 1 应被移出，报告: {report}"
```

测试**明确要求 `1` 必须被移走**，否则测试失败。这意味着：

1. 该危险行为不是一个疏漏，而是**被写进验收标准的预期行为**；
2. 任何后续修复都会让这条测试变红，形成「修复即破坏测试」的阻力；
3. 20 passed 中有 1 条通过，恰恰是**这条危险的通过**。

### 2.4 开发方已意识到风险，但未修

开发方在沟通中自述：「我的别名逻辑里 `T01` 会匹配裸 `1`，若直接在真机跑去重，会把用户的 `1` 号模板也移走。所以真机清理不能用激进别名匹配。」

**它识别出了风险，选择的应对是「不在真机执行」，而不是「修正代码」。** 代码仍在生产路径上、默认启用。这只把风险从「本轮触发」推迟到「下次构建触发」。

### 2.5 处置要求

1. **移除裸编号别名**（`'1'`、`'23'`）。裸编号与 `T01`/`T23` 的映射缺乏可靠依据，且与用户既有模板库直接冲突。
2. 去重判定不得仅凭名称模式。**必须增加内容级判据**：仅当兄弟目录的 `.moti` 与构建产物**结构同源**（如 `reference_base` 出身一致、层级数匹配）或 sha 相同/已知历史 sha 时，才允许移出。
3. 无法确认同源时，**默认不移动**，只输出警告清单。
4. 同步修改 `test_r22_a40_dedup.py` 第 78 行断言：`'1'` **不应**被移走；另建独立用例证明 `01_领衔呈现`（内容确为旧版）会被移出。
5. 增加回归用例：**构造一个与目标无关的 `1` 目录，断言其安装后仍然存在**。

## 三、缺陷 A-42（P1）：用户真实遭遇的闪退至今未被解释

### 3.1 用户原始反馈（未变）

> 「我看到了有很多个版本，不知道到底是哪一个版本是你们做出来的最新的。还有一个问题，就是有一些版本一触碰就会闪退。」

### 3.2 开发方的回应与问题

开发方在沟通中声称：

- `~/Movies` 里 T01/T23 各只存在一个，已满足唯一性；
- `1`–`50` 是用户 10-19 生成的独立模板库，**空 Media 是纯文本字幕的正常态**；
- 已知坏 sha `14fa354d` 只在只读卷，不在 `~/Movies`。

**但审核方核验交付物后发现：**

```
报告全文检索 "Movies|PSD婚礼|1-50|独立模板|空Media正常"
→ 仅 1 处命中，且内容是「批量状态文件落 ~/Movies/.../PSD婚礼字幕」，
  与版本扫描、唯一性判定、1-50 库性质 完全无关

docs/r22_evidence/ 全部内容
→ 只有 a40_demo.txt（577 字节）
```

**判定：上述三条结论在交付物中没有任何证据支撑。** 这恰好违反 R22 §6.2「每一个数值必须附完整命令与原始输出片段」的硬性要求，也重演了 A-38 的模式（结论写在聊天里，落不到可核验文件）。

### 3.3 更关键的矛盾未被处理

1. **用户看到「很多个版本」，开发方说「各只有一个」。** 二者直接冲突。可能的原因：用户看的是 FCPX 模板浏览器里 `1`–`50` 与 `T01`/`T23` 混排（视觉上就是「很多个」），而开发方只统计了名称含 `T01`/`T23` 的目录。**这个口径差异没有被说明，也没有被核实。**
2. **「空 Media 是正常态」与此前 A-25 的判定矛盾。** A-25 曾作为 P1 缺陷记录（23 号 `Media/` 为空），当时判为缺陷；现在同一现象被称为正常。**两种定性必须有明确适用边界，否则后续无法判断「空 Media 该不该报错」。**
3. **「一碰就闪退」的具体版本从未被指认。** 没有崩溃日志、没有版本 sha、没有复现步骤。这是整个 A-40 最关键的事实，至今空白。

### 3.4 处置要求

1. 提交 **`~/Movies/Motion Templates.localized/Titles.localized/PSD婚礼字幕` 的完整目录清单**，附命令与原始输出：每个子目录名、`.moti` 个数、sha256、mtime、`Media/` 文件数。
2. 明确指出**用户看到的那「很多个版本」具体是哪几个目录**，逐一对上 sha。
3. 若用户曾遭遇闪退，请取 macOS 崩溃日志（`~/Library/Logs/DiagnosticReports/` 下 Motion/FCP 相关 `.crash` 或 `.ips`），定位崩溃时的模板路径。**没有崩溃日志，A-42 不能关闭。**
4. 明确写下「空 `Media/` 在何种条件下属正常、何种条件下属缺陷」的判据，并说明 A-25 当时的定性如何与之统一。
