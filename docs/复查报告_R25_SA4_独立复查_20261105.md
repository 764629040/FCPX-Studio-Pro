## 4. 对抗性审查发现（含严重度 / 证据 / 整改建议）

### 我发现了 7 个问题

---

#### 问题 1（P1）：可见智能对象 + `smart_object_policy='skip'` 路径守恒被破坏，且「跳过」根本没跳过 —— C-2 测试未覆盖该路径

**位置**：`core/psd_parser.py` L1099-1204（else 分支）。

**机理**：可见智能对象走 else 分支时，L1107 把 `disposition` 置为 `"ignored"`，但**没有 `continue`**，代码继续执行到 L1203 `layers_info.append(layer_info)` —— 该层既计入 `output_layer_count`（= `len(layers_info)`）又被 `ignored_count` 统计入 `skipped_layer_count`，双重计数，恒等式 `input == output + skipped` 必然破坏。更糟：被「显式跳过」的层实际仍进入输出层列表，参与下游转换 —— skip 语义完全失效。

**复现（SA-4 实测）**：

```
$ python3 -  # 构造可见智能对象 PSD（FX.build_visible_smartobject_psd）+ parse_psd_file(p, smart_object_policy="skip")
conservation: {'holds': False, 'input_layer_count': 12, 'output_layer_count': 7,
               'skipped_layer_count': 7, 'detail': '守恒被破坏: input=12 output=7 skipped=7 (差 -2)'}
SO: Image01 disposition= ignored ...
SO: 2303edcbb5dfad77a452cab79b4fabd disposition= ignored ...
layers_info 中的 smartobject 数: 2  disposition: ['ignored', 'ignored']
```

**为什么 C-2 测试没抓到**：`test_smart_object_skip_policy_records_reason` 用 `copy_complex_psd`（智能对象默认**隐藏**），隐藏层在 L869 `elif not layer.visible:` 提前分流，永远到不了 L1107 的 skip 分支。测试断言的 skip 原因文案其实来自 L874-878 的「隐藏+skip」拼接文案。**可见 SO + skip 组合零覆盖。**

**加重因素**：`parse_psd_file` 内守恒被破坏时只 `diagnostics_warnings.append(...)`（L1289-1294），不抛异常、不阻断 —— 产品管线里坏结果会照常出货。

**整改**：① skip 分支处理完诊断后不生成 layer_info（或 `continue`）；② 补一条「可见 SO + skip」夹具测试（改 `build_visible_smartobject_psd` + skip 策略）；③ 考虑把守恒破坏升级为可配置的硬失败。

#### 问题 2（P1）：无 scipy 时，flatten 降级层产出指向**不存在 PNG** 的 relativeURL，构建 status=ok，全程静默 —— 完整性校验存在盲区

**位置**：`core/motion_builder.py` L638-653（构建期 PNG 重提取 `except Exception: pass` 吞错）、L199-201（无 PNG 时仍 fabricate `Media/element_XX.png` 引用）、L808-812（完整性校验只查「已设置 fallback_png_path 的层」）。

**SA-2 的说法是**「本环境若无 scipy，展平出的 PNG 可能缺失，但图层仍应被记为 degraded（绝不静默丢弃）」。图层确实没丢（C-8 层面成立），但**最终交付物是坏的且无任何用户可见警告**：

**复现（SA-4 实测，无 scipy 环境）**：

```
$ python3 -  # build_visible_smartobject_psd → parse（默认 flatten）→ build_template_atomic
Failed to update preview image: Stroke effects require: scipy ...
build status: ok
relativeURLs: ['Media/element_01_Element02.png', 'Media/element_02_Element01.png',
               'Media/element_03_Image02.png', 'Media/element_04.png',
               'Media/element_06_2303edcbb5dfad77a452cab79b4fabd.png']
Media dir files: ['element_01_Element02.png', 'element_02_Element01.png',
                  'element_03_Image02.png', 'element_06_2303edcbb5dfad77a452cab79b4fabd.png']
MISSING media refs: ['Media/element_04.png']        # ← .moti 引用了不存在的文件
kind!=type 且无 PNG 仍进输出的层: ['Image01']
```

解析期 PNG 导出失败的警告（psd_parser L1141-1147）**仅在 `extract_fallback_pngs=True` 且给了 `png_output_dir` 时才写**；构建期重提取失败被 `except: pass` 静默吞掉；完整性校验第 4 条因 `fallback_png_path is None` 直接放行。用户在 Motion 里拿到一个「缺失媒体」的图层，从头到尾没有任何提示。带描边的智能对象（composite 依赖 scipy）在本机必中。

**整改**：① `verify_bundle_integrity` 增加规则：所有 media 层的 relativeURL 必须在 Media/ 中真实存在，缺失即 fail；② 构建期重提取失败必须写入结果 warnings（不许裸 `pass`）；③ 要么装 scipy 进依赖（`requirements.txt`），要么在 UI/诊断中把「本机无法合成带描边图层」升级为显式告警。

#### 问题 3（P2）：C-10「缺字可见标记」只活在 JSON 里 —— .moti 输出写原始文本，GUI 无任何消费

**证据**：
- `core/motion_builder.py` L384-386：`text_elem.text = info.text` —— 写入 .moti 的是**原始文本**，不是 `marked_text`（□ 标记版）。
- `grep -rn "marked_text|highlight_missing_font|missing_glyph_visible_marker" gui/*.py` → **0 命中**。GUI（canvas_view / inspector_panel / main_window）没有任何代码读取这些字段。

即：□ tofu 标记与「缺字体高亮」只存在于诊断 JSON 的 `marked_text` / `highlight_missing_font` 字段，用户在 GUI 和最终 Motion 模板里都看不到。任务单 C-10 的「诊断面板必须高亮」在 GUI 侧**未接线**。测试本身没错（它只测 parser/诊断层），但交付口径上「可见标记」对用户不可见。

**整改**：motion_builder 写 .moti 文本时对缺字层使用 `marked_text`（或提供开关）；GUI 诊断面板/检查器消费 `highlight_missing_font` 做视觉高亮；补一条端到端断言「缺字层在 .moti 的 id=369 文本中含有 □」。

#### 问题 4（P2）：沙箱 shim 使 pytest `tmp_path` 二次运行必炸（EEXIST 37 errors）—— C 域测试的可复现性受环境影响，且 D 域与 C 域规避方式不一致

**整改**：C 域测试统一改为 mkdtemp 自管夹具（与 d02/d03 同法），或在项目 README/复查指引中固化「跑前清理」步骤。

#### 问题 5（P3）：D-2/D-3 的「GUI 接线」测试是纯源码字符串 grep，只能证明字符串存在

`test_canvas_wires_writeback_and_moti_path` / `test_main_window_publishes_moti_path` 只 `assert "set_moti_path" in src` 等。字符串出现在源码 ≠ 运行时路径被执行（写在注释/死分支里也能过）。PyQt6 缺失导致无法 headless 端到端，这是已知环境限制且 SA-3 已披露，但结论上 GUI 拖拽写回/锁定持久化的**运行时行为未被任何测试验证过**。核心逻辑（moti_layer_io）测试质量没问题：真实构建 .moti、写回后**重新解析 XML** 并直接断言 `parameter[@id='101']/parameter[@id='1']` 的 value（`test_position_writeback_updates_real_xml_param_tree`），原子性两条（层不存在不落盘、os.replace 失败原文件字节不变）都是真断言，不是「调函数不抛异常」型假测试。

**整改**：有 PyQt6 的机器上补一条 smoke 测试（QApplication + 模拟 itemChange 提交 → moti 落盘），或至少用 AST 解析替代字符串 grep。
