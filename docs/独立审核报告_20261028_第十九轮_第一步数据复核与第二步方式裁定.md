## 二、第二步方式裁定：采用方案 A

### 2.1 你的两个方案

- **方案 A**：用 `build_template_atomic` 直接输出到已装路径，让备份机制自然生效；
- **方案 B**：先手工备份，再 `cp` 覆盖。

### 2.2 裁定：**方案 A**，理由如下

| 维度 | 方案 A（构建函数） | 方案 B（手工 cp） |
|---|---|---|
| 完整性校验 | 走 `_validate_template_bundle`，`.moti` >1KB、XML 合法、缩略图非空、降级 PNG 全部存在，缺一即拒 | 无，靠人眼 |
| 失败回滚 | 异常时 `shutil.rmtree(tmp)` + `os.rename(backup→output)` 自动还原 | 无，出错即半成品 |
| 产物一致性 | 临时目录内构建后 `os.replace` 原子提交 | `cp -r` 非原子，中断即残 |
| 与线上路径一致性 | 与 GUI「保存为模板」走同一条代码路径 | 偏离产品实际路径，装了等于没验 |
| 备份命名 | `_bak_<timestamp>` 自动 | 需人工保证不重名 |

**方案 A 唯一的代价是备份目录落点问题（见 §三 A-36），但该问题在方案 B 里同样存在**——手工备份你也得选一个位置，放在扫描树内一样会被扫到。所以这不是「A 有 B 没有」，而是「选 A 顺带把这个问题暴露出来」。

**结论：用方案 A。**

### 2.3 但方案 A 不是无条件执行——四项前置必须满足

| 编号 | 前置条件 | 原因 | 验证方式 |
|---|---|---|---|
| **P-1** | 先 `ls -ld` 确认已装 `1`、`23` 是**真实目录还是符号链接** | `os.rename` 对符号链接只移动链接本身，随后 `os.replace` 会建出**真实目录**，若原本是链接则链接架构被破坏 | `ls -ld "<已装路径>/1" "<已装路径>/23"` |
| **P-2** | 确认备份目录落点，并在第三步验证后**手动移出扫描树** | 见 A-36 | 见 §三 |
| **P-3** | 确认 `Titles.localized/PSD婚礼字幕` 本身是否为符号链接；若是，确认备份与替换发生在**外部真实目录**内 | `os.rename` 跨文件系统会抛 `EXDEV` | `ls -ld "<group 目录>"` |
| **P-4** | 第二步**逐模板串行**执行（先 01 后 23），不要批量 | 任一失败时保留另一个不动，回滚面最小 | 分两次调用 |

**P-1 是硬门槛。** 如果 `1`/`23` 是符号链接，方案 A 必须先改造（在 `build_template_atomic` 内对 `os.path.islink(output_dir)` 分支处理），否则会静默破坏链接架构。**在此项确认前，不要执行第二步。**

## 三、新增缺陷 A-36（P2）：备份与临时目录落在模板扫描树内部

### 3.1 事实（源码实证，非推断）

`core/motion_builder.py`：

- 第 548 行：`tmp_build_dir = f"{output_dir}_tmp_build_{os.getpid()}_{int(time.time()*1000)}"`
- 第 629 行：`backup_dir = f"{output_dir}_bak_{ts}"`

两者都是 **`output_dir` 的同级目录**。当 `output_dir` = `.../Titles.localized/PSD婚礼字幕/1` 时：

- 临时目录 → `.../PSD婚礼字幕/1_tmp_build_<pid>_<ms>`
- 备份目录 → `.../PSD婚礼字幕/1_bak_20261028_xxxxxx`

即**落在 Motion / FCPX 的模板扫描目录内部**，与真实模板 `1`、`23` 同级。

### 3.2 风险

备份目录内**包含完整的 `1.moti`**（`os.rename` 整目录搬走）。Motion 的模板浏览器按「组目录下的子目录」枚举，很可能把 `1_bak_20261028_xxxxxx` 也列成一个模板。

后果：FCPX 模板浏览器出现**重名或近重的幽灵模板**，用户可能误选旧版（正是 comp 尺寸错误的那个版本）。

**这一条我标注为「高概率风险，待真机确认」**——枚举规则属 Motion 内部行为，Linux 沙箱无法证实。但「把备份放在被扫描目录里」本身就是设计缺陷，不依赖枚举规则是否成立即可判定。

### 3.3 定性与建议

- **定级 P2**：不阻断安装（备份目录可事后移走），但会污染用户可见的模板列表，属必须处理的交付质量问题。
- **本轮不必改代码**：第二步验证完成后，把 `*_bak_*` 移到扫描树外（如 `~/Movies/_psd_subtitle_backups/`）即可。
- **建议后续整改（A-36 正式修复）**：给 `build_template_atomic` 增加 `backup_root` 参数，默认备份到 `~/Movies/_psd_subtitle_backups/`，或备份目录加 `.` 前缀（`.1_bak_xxx`）借隐藏属性规避枚举。**加隐藏前缀是更稳的做法**，因为不依赖用户额外目录。
- **临时目录风险较低**：`_tmp_build_` 在成功后即被 `os.replace` 消费掉，只在构建**失败但未清理**时才残留；现有异常分支已 `shutil.rmtree`，残留概率低。

## 四、命名裁定：建议改为 `T01_...` / `T23_...`

### 4.1 先纠正一个前提

你担心「改名会影响 FCPX 里显示的模板名」——**确实会**，这一点你的直觉是对的。但改名不是纯粹的偏好问题，它背后有一条**项目自身的硬约束**：

`_validate_template_bundle`（`core/motion_builder.py` 第 681 行）要求：

```
moti_path = os.path.join(bundle_dir, f"{template_name}.moti")
if not os.path.isfile(moti_path): raise FileNotFoundError
```

而 GUI 侧（`gui/main_window.py` 第 562、574 行）用同一变量同时作**目录名**和**`template_name`**：

```
base_name = os.path.splitext(os.path.basename(self.current_psd_path))[0]
template_dir = os.path.join(target_group_dir, base_name)
build_template_atomic(output_dir=template_dir, template_name=base_name, ...)
```

**推论（重要）：`.moti` 文件名必须与模板目录名一致。**

### 4.2 这直接决定了两条路的成本

| 命名 | 能否直接复用 `build_staging/` | 代价 |
|---|---|---|
| 保持 `1` / `23` | **不能**。staging 里是 `T01_领衔呈现_竖版.moti`，装进名为 `1` 的目录会过不了校验 | 必须**重新构建**（`template_name="1"`/`"23"`），或手工改名 `.moti`（绕过校验，不推荐） |
| 改为 `T01_领衔呈现_竖版` / `T23_含装饰_横版` | **能**，staging 已是此命名，与 §一 已复核的产物**字节一致** | 无需重建，直接装已复核的产物 |

### 4.3 裁定

**建议本轮改为 `T01_领衔呈现_竖版` / `T23_含装饰_横版`**，三个理由：

1. **直接用已复核产物**，不引入「重建后未经复核」的新变量——这是审核角度最看重的；
2. `1` / `23` 无信息量，用户在 FCPX 里无法区分；
3. 旧版 `1` / `23` 本身是**坏的**（01 comp 方向错、23 缺 2 个 Media），从未真正可用，因此不存在「历史工程引用了它、改名会断链」的实际损失。

**但有一条例外**：如果你**已经**把旧 `1` / `23` 拖进过某个 FCPX 工程时间线，改名后旧引用会变「缺失模板」，需要重新套用。**如果存在这种情况，就保持 `1` / `23`，改为按 §4.2 第一行执行重建。**

**请明确告知属于哪种情况**，我再确认最终路径。
