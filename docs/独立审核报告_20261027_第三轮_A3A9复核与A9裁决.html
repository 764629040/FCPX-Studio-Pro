四、A-9 定性裁决（本次唯一请求裁决项）

开发方判定：A-9 系「调用方未开启 extract_thumbnails」，非渲染缺陷，故未改代码，并询问是否要加代码级兜底。

4.1 裁决结论

第一层：接受「不是渲染器缺陷」这一定性。审核方撤回上一轮的相反判断。

证据（审核方独立取得）：

证据 内容
默认值core/psd_parser.py:594 extract_thumbnails: bool = True —— 默认就是开启
产品主路径gui/main_window.py:407-410 调用 parse_psd_file(..., extract_thumbnails=True)
切片真实产出four_state.psd 8 个文本层全部有切片（486 B ~ 3,092 B）；complex_layers.psd 的 Text01 4,520 B、Title 12,374 B
画面佐证截图 17 左栏「PSD 原稿预览」确实渲染出「领衔呈现 / 新娘 朱永宏 / 新郎 陈晗 / 镇雄 / CITY」及对应英文列

结论：上一轮「左栏不渲染文本」的判断由审核方撤回，责任不在渲染器。开发方这一处判断是对的。

第二层：不接受「因此无需任何代码改动」。要求两处最小修正，但明确不要加渲染兜底。

理由一——产品自己就是那个"未开启的调用方"，口径分裂：

core/psd_parser.py:1164 的 generate_diagnosis_report 内部固定 extract_thumbnails=False。于是同一份 PSD 在两条链路上对"切片是否可用"给出不同答案：诊断链路永远看不到切片，画布链路看得到。用户若先看诊断、再看画布，会得到互相矛盾的印象。这不是"某个外部调用方忘了开"，而是产品内部两条链路开关不一致。

理由二——降级文案把三种成因写成了同一句话：

gui/canvas_view.py:298/314 中 is_empty_or_group 在以下三种情况下都为 True：

  1. layer_type == "group"（图层组）
  2. is_empty 为真（真空图层）
  3. pixmap is None or pixmap.isNull() —— 包含"切片字节存在但 loadFromData 解码失败"

而 :370 对非 group 一律显示「⚠️ 空图层 / 无像素内容」。第 3 种情况被说成"空图层"，正是本项目反复强调要禁止的用占位说明掩盖真实失败。

4.2 具体处置要求

  • 不要加"切片缺失时回退实时绘制文字"的兜底。理由：那会重新引入字体度量偏差（A-3 刚刚统一），并且用矢量文本冒充 PSD 原始栅格，等于用另一种"看起来对"掩盖"实际没取到"，与本项目红线相悖。
  • 要做两处最小修正：
  1. 统一诊断链路口径：generate_diagnosis_report 与画布使用同一 extract_thumbnails 取值；若确需为性能关闭，必须在诊断报告中显式标注「本次诊断未提取切片，切片可用性未知」，不得留白。
  2. 文案二分：把「空图层/无像素」与「切片解码失败」拆成两句不同提示（前者灰、后者橙并给出图层名），让"取不到"和"本来就没有"在界面上可区分。

六、本轮新发现

A-10（跨平台缺陷，建议 P0）无 AppKit 平台把「无法检测」误报为「字体未安装」

  • 位置：core/psd_parser.py:765-770（判定短路）与 check_font_availability（AppKit 导入失败即 return False）
  • 机制：无 AppKit 时 check_font_availability 恒返回 False；:765 的 if not is_font_available 抢在 :767 的 elif glyph_cov["status"] == "unverifiable" 之前命中，于是所有字体都被判成 font_missing。
  • 审核方实测（同一函数对三个字体）：
字体 check_font_availability check_font_glyph_coverage().status
HelveticaFalseunverifiable
CormorantInfant-RegularFalseunverifiable
PingFangSC-RegularFalseunverifiable

即：字形检测模块已经正确回答「无法验证」，却被上游的可用性判定覆盖成「未安装」。

  • 影响：Windows / Linux 版会把「查不到」说成「字体没装」，误导用户去装一个可能本来就有的字体；同时四态分化在该平台退化为单一态，A-2 的分化成果实际失效。
  • 与自述契约冲突：core/psd_parser.py:96-97 明确写「不得把无法验证当成未安装」。
  • 建议修法：check_font_availability 与 check_font_glyph_coverage 一样返回三态（available / missing / unverifiable），:765 仅在三态为 missing 时判 font_missing。

A-11（文案，建议 P1）「空图层」与「解码失败」共用一句提示

  • 位置：gui/canvas_view.py:298/314/362-370
  • 问题：is_empty_or_group 把「图层组 / 真空层 / pixmap 解码失败」三种情况合并，非 group 一律显示「⚠️ 空图层 / 无像素内容」。
  • 现网影响：截图 17 该占位框被判为"空图层"，但审核方无法从界面区分它是"本来就没像素"还是"切片拿不到/解码失败"——这正是本次 A-9 争议的成因之一。
  • 建议：文案二分（详见第四节）。

A-12（标注错误，建议 P2）画板预设与实际尺寸相反

  • 证据：截图 17 顶部下拉显示「1080P 全高清 (1920 × 1080)」、模式标「模板 (16:9)」，而同排 W=1080、H=1920，画板实为竖版 9:16。
  • 影响：用户会误以为当前是横版 16:9 工程；导出前据此判断画幅将出错。
  • 建议：预设标签随实际 W/H 联动，或在竖版时显示「竖版 1080×1920 (9:16)」。

A-13（对照失真，建议 P0）左栏「PSD 原稿预览」整幅错位约 200 px

  • 证据：截图 17 中同一组图层，左栏文字位于 y≈480–580，右栏位于 y≈280–450；左栏「领衔呈现」列更直接落在绿色画板框左外侧。
  • 量化：审核方按画板中心换算公式反算屏幕坐标——
图层 左栏（按旧中心 960,540 预测） 左栏实测 右栏（按当前画板，两栏应一致）
领衔呈现 x129 px≈122–155 px应在框内、明显偏右
领衔呈现 y531 px≈480–580 px≈280–450 px

偏差量 (1920−1080)/2 × 0.467 ≈ 196 px，与实测 ~200 px 吻合。

  • 根因（代码定位）：OriginalLayerGraphicItem.__init__ 在构造时把 artboard_w/artboard_h 固化为实例字段（gui/canvas_view.py:292-296，由 :517 传入）；而 set_artboard_resolution（:469-472）只更新视图自身字段并重绘画板框，不会重建或重算已存在的图元。于是竖版 PSD（1080×1920）载入后，左栏图层仍在用默认 1920×1080 的中心 (960,540) 换算位置，右栏 ConvertedLayerGraphicItem 走 motion_pos 不受影响。
  • 对照实验（几乎可视为受控验证）：截图 19 是横版 1920×1080，恰好等于代码里写死的默认值，两栏对齐良好——竖排英文列在左框内的相对位置 (700−33)/737 = 0.905，右栏 (1500−833)/735 = 0.907，相差 0.002；而截图 17 是竖版 1080×1920，同一组图层两栏相距约 200 px。尺寸等于默认值时对齐、不等于默认值时错位，与"画板尺寸未下发到左侧图元"的推断完全吻合。
  • 影响：直接破坏「并排对照」这一核心验收口径——两栏看似都渲染了，但同一图层并不在同一相对位置，用户无法据此判断转换是否正确。这比"某处文案错字"严重得多，故建议列 P0。
  • 建议修法：set_artboard_resolution 中对 OriginalLayerGraphicItem 重新下发画板尺寸并触发 update_geometry()；或将画板中心改为从视图实时读取而非构造时固化。
