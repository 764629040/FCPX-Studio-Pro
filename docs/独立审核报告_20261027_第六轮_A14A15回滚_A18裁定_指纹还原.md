## 2. `canvas_view.py` 指纹偏差：**已完整还原，原件交付**

### 2.1 偏差精确定位

| 项目 | round5 | 当前 |
|---|---|---|
| 大小 | 42471 | 42485（+14） |
| SHA-256 | `62a45b1b…03325` | `245996ba…60b29` |

开发方称差异为「+14 字节 / 4 行，回滚时空行未逐字节还原」。

**审核方定位结果与「4 行」不符，实为 1 行。** 依据：

1. 当前文件**没有任何纯空白行**（`ws_only_lines_with_content = 0`），故「4 个空行」假设直接被证伪。
2. 用 312 缓存的 code object 比对行号位移：**前 265 行偏移为 0，自旧第 266 行起偏移变为 +1**
   （`Counter({1: 47, 0: 10})`）。说明全文只在某一点**插入了一行**。
3. 该行长度为 13 字节（13 + 换行 = 14 字节）。逐一试删 18 个长度为 13 的行，
   仅一处使 SHA 精确命中 round5 目标值：

```
*** MATCH: 删除当前文件第 223 行 b'            #'  -> SHA 精确等于 62a45b1b…
```

**即：多出来的唯一内容是一个「            #」空注释行，紧接在 `# 矢量文字渲染` 注释之后、`painter.setPen(QColor("#FFFFFF"))` 之前（当前第 222~224 行之间）。**

该行是注释，对字节码完全无影响——这正是 57/57 字节码一致的原因。

## 3. A-18 裁定：**不成立，建议驳回**

开发方报告：「`QFont(int)` 按 point 解释，而 PSD 的 `font_size` 是像素。实测 `QFont(34)` 实际像素高 63px，`setPixelSize(34)` 为 48px，前者大 1.31 倍。即当前右栏字形比 PSD 原稿偏大约 31%。」

### 3.1 该结论的前提是错的

开发方的量法是「同一个数字分别喂 `setPointSize(34)` 与 `setPixelSize(34)`」。
但**生产代码并不这样调用**。真实链路是：

```
PSD font_size(px)  →  text_render_font_size()  →  ×0.75  →  QFont(family, pt)  →  Qt 按 DPI(96) 换算回 px
```

`×0.75` 正是「像素 → point」的换算系数（1pt = 1.333px，1/1.333 = 0.75），
它与 Qt 内部「point → 像素」的换算**相互抵消**，因此字形高度本就贴近 PSD 原稿。

### 3.2 实测真实链路偏差

调用生产函数 `text_render_font_size()`，并与「按 PSD 像素直接 `setPixelSize`」的真值比较：

| PSD 字号(px) | 渲染 pt | 实际高度 | 真值高度(px) | 偏差 |
|---|---|---|---|---|
| 18 | 14 | 26 | 24 | **+8.3%** |
| 24 | 18 | 33 | 33 | **0.0%** |
| 34 | 26 | 48 | 47 | **+2.1%** |
| 48 | 36 | 66 | 66 | **0.0%** |
| 100 | 75 | 138 | 138 | **0.0%** |
| 122 | 92 | 169 | 167 | **+1.2%** |

**偏差区间 0% ～ +8.3%，不存在 31%。** 且偏差随字号增大收敛到 0，
残余来源是 `int(round())` 取整，属小字号量化误差，非系统性放大。

（旁证：开发方自己测 `QFont(34)` 得 63px，审核方在 96 DPI 下测得 53px，
说明该数值强烈依赖 DPI/字体环境，本就不是稳定口径，不适合作为缺陷依据。）

### 3.3 A-3 的 ×0.75 约定是正确的

A-3 测试断言 `font_size=100 → size == 75`，审核方实测该路径高度偏差 **0.0%**。
**×0.75 是正确的单位换算，不是需要推翻的历史包袱。**

若按开发方设想改为 `setPixelSize(font_size)` 并去掉 ×0.75，反而会：
1. 使 `text_render_font_size()` 的返回值语义从 pt 变为 px，破坏 A-3 已过审的断言 `size == 75`；
2. 在非 96 DPI 环境（如 macOS Retina，DPI 更高）产生**真实的**字号偏差——
   即把一个当前不存在的问题，换成一个在不同 DPI 下才暴露的新问题。

**裁定：A-18 不予立案。不建议任何改动。** 推翻 A-3 将引入真实风险，收益为零。

> 说明：开发方「不越权改动已过审约定、先送审」的做法本身是正确的工作方式，
> 这次是判断依据有误，不是流程有误，审核方对此予以肯定。

## 4. 新发现 A-19：`tools/` 未纳入指纹清单（受控面缺口）

本轮唯一交付物是 `tools/round.py` 与 `tools/dsh-plugin/`（5 个文件）。
核查 round6 清单：

```
inventory total = 30

```

**这些文件全部不在指纹清单内。** 后果：

1. 审核基线「以指纹清单为唯一依据」出现盲区——本轮实际新增的代码不受任何指纹约束；
2. `round.py` 具备写 `docs/`、执行子进程、生成清单的能力，属**高权限工具**，却无指纹保护；
3. 若该工具日后被修改，审核方无从发现。

**建议**：将 `tools/round.py` 纳入受控清单；`tools/dsh-plugin/` 若确定不装，可移出项目或明确排除。
清单项数变为 31（或扣除插件后 30+1）。

### 4.1 round.py 只读卷守卫的稳健性问题（同源，一并提示）

```python
FORBIDDEN_ROOTS = ("/Volumes/NO NAME/128",)
```

守卫为**路径字符串前缀匹配**，且硬编码单一卷名。当前项目 `canonical_path` 为
`/Volumes/摄影师工具箱128GB/未命名文件夹/FCPX_Studio_Pro`，两者不同名。
即：守卫只防了 128 卷，未防「写入任意其他卷」，也未覆盖沙箱映射路径（如 `/mnt/local/128`）。

在开发方 macOS 环境上**当前可用**，但属于「靠记住卷名」的脆弱实现。
建议改为：写入前校验目标路径必须位于 `PROJECT_ROOT` 之内（白名单），而非黑名单枚举。

**评价**：退出码直接取 `subprocess.returncode` 并在日志末行写 `PYTEST_EXIT_CODE=N`，
这一设计确实从结构上消除了历史上「tee 取错退出码」的事故，**该部分设计正确且有价值**。
