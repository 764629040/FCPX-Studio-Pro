## 1. A-10 裁决：**接受，属根因修复，不判定超限**

开发方第 1 点询问「改动面是否超出最小修正」。结论：**未超限**，理由如下。

### 1.1 只调判断顺序确实无法修复

原缺陷不是顺序问题：`check_font_availability()` 的返回类型是布尔，而语义需要三态（可用 / 不可用 / **无法检测**）。布尔值把后两者压成同一个 `False`，任何顺序调整都无法把「无检测能力」与「未安装」区分开。新增三态接口是唯一可行路径。

### 1.2 兼容性与侵入面已核实

- 布尔包装 `check_font_availability()` 保留，内部转调三态接口，旧调用契约不破。
- 产品代码中 `check_font_availability` 的调用点：**仅测试与注释**，无 GUI/核心流程依赖，改动不产生行为外溢。

### 1.3 成效实测

`four_state.psd` 8 个文字层：

```
detection_status 集合 = {unverifiable}
font_missing 计数 = 0
```

即：无 AppKit 平台不再把「无法检测」误报为「字体未安装」，A-10 的判定目标达成。

### 1.4 必须标注的验证边界（记 A-16，不阻塞）

本环境**只能触达 `unverifiable` 这一态**。`detected` / `font_missing` / 字形缺失三态在 Linux 下无法被真实触发，因此「四态分化」在**无 AppKit 平台的可达性**已被证伪为误报，但**四态在 macOS 上的语义正确性仍未由审核方直接观测**，只能由代码路径与开发方 macOS 日志间接支持。列为 A-16，留待 macOS 环境补证，不作为退回项。

### 1.5 撤回一项疑似缺陷（避免误伤）

本轮初步比对发现 8 个文字层中有 6 层的 `original_font` 与本层声明字体不一致，曾怀疑为映射错位。逐层取值核对后**撤回该怀疑**：

- `original_font` = PSD 声明的原始字体，取自 `resource_dict["FontSet"]` 首个非 Adobe 隐藏字体，逐层取值与 FontSet 首项**一一对应**（`PingFangSC-Regular` / `Helvetica` / `CormorantInfant-Regular` 等完全吻合）。
- `font_name` = 实际渲染用字体，按文本是否含中文回退到 PingFangSC 或 Helvetica。

两者是**语义不同的两个字段**，不是同一个值被写错。此处不构成缺陷。

## 2. A-13：**修复成立**

- 竖版 1080×1920 下，正序与逆序两种图层遍历均 **0 错位**，`worst_dev = 0.00` 画板单位。

### 关于「420px 与约 200px」的差异（开发方第 2 点）

**不是矛盾，是单位不同。**

- 开发方给的 420 是**画板单位**，审核方实测约 200 是**屏幕像素**。
- 当前画布缩放比约 **0.44**：420 × 0.44 ≈ **186 屏幕 px**，与审核方实测约 200 px 同源同量级，差异来自缩放取整与量测位置。
- 两者方向一致、量级一致，可互相印证，不构成对修复结论的反证。

## 3. A-9：**两处最小修正均已到位**

| 修正项 | 实测 |
|---|---|
| `parse_psd_file` 默认 `extract_thumbnails` | `True` |
| `generate_conversion_diagnosis_report` 默认 `extract_thumbnails` | `True` |
| 占位原因四分 | `group` / `empty_layer` / `no_slice` / `decode_failed` |

占位判定顺序为：先按图层语义（图层组 → 真空图层），再看像素（无切片 → 解码失败），四类**文案各不相同**：

- `group`：📁 图层组容器 / 无独立像素
- `empty_layer`：⚠️ 真空图层 / 尺寸为零或无有效像素
- `no_slice`：🖼 未生成原稿切片 / 请开启 extract_thumbnails
- `decode_failed`：❌ 原稿切片解码失败 / 数据可能损坏

上一轮 P1 项 A-11（「空图层」与「解码失败」文案混同）与 A-9 改动落在同一段占位逻辑，现已可区分。A-11 建议在下一轮一并勾销，需开发方确认是否同轮处理的意图。

## 5. A-12：**未处理，本轮实测确认仍存在**

审核方在离屏环境实际实例化画布容器并执行真实交互，读数如下：

| 操作 | 预设下拉显示 | 方向按钮 | 实际 W × H |
|---|---|---|---|
| 初始 | 1080P 全高清 (1920 × 1080) | 🔄 横版 (16:9) | 1920 × 1080 |
| 选竖版预设 | 竖版 1080P 抖音/短视频 (1080 × 1920) | 🔄 竖版 (9:16) | 1080 × 1920 |
| **点击方向切换** | **竖版 1080P 抖音/短视频 (1080 × 1920)** | 🔄 横版 | **1920 × 1080** |

点击方向切换后，画板已是横版 1920×1080，方向按钮也变成「横版」，但**预设下拉框仍写着「竖版 1080P 抖音/短视频 (1080 × 1920)」**，标签与真实画板直接矛盾。

成因已定位：方向切换只交换 W/H 两个数值，并更新方向按钮文字；`_on_preset_changed` 会同步按钮文字，但**两条路径都不会反向同步预设下拉框的选中项**，因此下拉框停留在旧标签。

**P2 定性维持，本轮未修。**

### 新发现 A-17（同源小缺陷）

方向切换路径设置的按钮文案是 `🔄 横版` / `🔄 竖版`，**丢失了 `(16:9)` / `(9:16)` 后缀**，而预设路径会带后缀。同一控件在两路径下文案不一致，属一致性瑕疵，建议与 A-12 一并修。

## 6. 新发现（视觉/可用性）

### A-14：44% 缩放下的文字栅格化质量差异

并排对照截图中右栏文字明显比左栏模糊。审核方做了 1:1 原生渲染核对：**「宏」等字在原生分辨率下笔画完整**（宀 + 一 + ノ + 厶 齐全）。

结论修正：这**不是字形丢失、不是几何裁切**，而是缩放视图下的采样/栅格化质量差异——左栏走位图缩放链路、右栏走文本重绘链路，两者在 44% 下清晰度不同。影响「并排逐字判读」的可信度，但不构成内容错误。评级 P2（观感/可判读性）。

### A-15：状态徽章拥挤

竖版排布时状态徽章贴住英文列，遮挡观感。P2 观感项。
